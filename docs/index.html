QA 에이전트 5개를 동시에, 검증된 보고서 1장으로

에이전트 하나로 앱을 시험하면 한 번에 한 경로만 걷고, 그럴듯한 첫 설명에서 멈춥니다. /qa는 일을 나눕니다. 서로 다른 영역을 맡은 서브에이전트 5개를 한꺼번에 띄우고, 찾은 문제는 보여 주기 전에 코디네이터가 직접 재현합니다.

두 팀, 각 다섯 명

/qa e2e · 시나리오 사용자

실제 브라우저에서 사용자처럼 화면을 조작합니다.

1

바뀐 핵심 흐름을 처음부터 끝까지

2

다른 역할과 권한

3

경계 입력: 빈 값, 최대 길이, 연타

4

상태와 중단: 새로고침, 두 번째 탭, 세션 만료

5

같은 API를 쓰는 주변 화면 회귀

/qa data · 데이터 분석가

최근 변경된 API와 쿼리를 실제 데이터와 맞춰 봅니다.

1

API 응답과 DB 행 대조

2

쿼리 논리: 조인, 필터, NULL, 중복

3

무결성: 고아 행, 나올 수 없는 상태 조합

4

집계와 시간: 날짜 경계, 시간대

5

변경 전·후 쿼리 결과 비교

/qa all은 두 팀을 한 번에 띄웁니다. 서브에이전트는 문제와 수정안만 만들고 아무것도 바꾸지 않습니다.

한 번의 실행

  1. 근거 수집

    저장소 지침과 --since 이후 git diff를 읽고, 바뀐 엔드포인트·쿼리·테이블·화면을 plan.md에 적습니다.

  2. 영역 나누기

    바뀐 경로마다 담당 영역을 정합니다. 영역끼리 계정·데이터·브라우저 세션을 공유하지 않습니다.

  3. 동시 실행

    메시지 하나로 서브에이전트 N개를 병렬로 띄웁니다. 모두 같은 브리프 양식을 받고 findings-n.md를 씁니다.

  4. 재현 검증

    원인이 같은 항목을 합치고 하나씩 재현해 CONFIRMED 또는 UNVERIFIED로 표시합니다. 시험 데이터와 브라우저 세션을 정리합니다.

  5. 보고와 적용

    심각도별 개수, 증거와 수정안이 담긴 표, 못 본 범위를 보고하고, 적용할 수정을 묻습니다. 승인한 것만 하나씩 적용하고 재현을 다시 돌립니다.

옵션

/qa [e2e|data|all] [target] [--agents N] [--model M] [--effort E] [--since REF]
인자기본값값
modee2ee2e data all
target현재 저장소와 dev 환경URL, 저장소 경로, 티켓 키, 기능 이름
--agents N5모드당 1-10
--model Msonnet (Sonnet 5.5)sonnet, opus, haiku, fable 또는 전체 모델 id
--effort Emediumlow medium high xhigh max
--since REF기본 브랜치와의 merge-basegit ref 또는 날짜

안전 장치

  • 운영 환경은 범위 밖입니다. 첫 쿼리 전에 DB 호스트를 확인합니다.
  • 서브에이전트는 읽기 쿼리만 쓰고, 저장소를 건드리지 않고, 외부에 아무것도 게시하지 않습니다.
  • 시험 데이터에는 QA-실행ID-번호 태그를 붙여 정리 목록에 남기고, 비밀값은 *** 로 적습니다.
  • 코드 수정과 데이터 쓰기는 사용자가 승인한 것만 적용합니다.

시험 실행

로그인과 CRUD가 있는 작은 데모 사이트에서 Sonnet 5.5 medium 에이전트 5개를 돌렸습니다(2026-11-09, 에이전트당 1.5-2.5분).

34원래 보고 건수
18원인별로 합친 건수
17코디네이터가 재현
1blocker

blocker는 세션 검사가 고정된 세션 문자열이 들어 있기만 하면 어떤 쿠키든 통과시킨 문제였습니다. 위조한 쿠키로 로그인 없이 API를 읽을 수 있었습니다.

이 실행에서 얻은 교훈 세 가지가 스킬에 들어 있습니다: 에이전트마다 이름 붙은 브라우저 세션 하나, 부하 데이터는 측정 직후 삭제, 담당 밖 문제는 한 줄만 적기.

사용자가 직접 /qa를 입력해야 실행됩니다. 에이전트가 스스로 시작하지 않습니다.
